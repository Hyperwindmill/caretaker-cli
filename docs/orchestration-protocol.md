# Caretaker Remote Orchestration — Protocol v1

This document specifies the HTTP polling protocol (version `1`) used by Caretaker's web server to register with a remote orchestrator, receive REST-envelope commands, and report results.

Because Caretaker runs on a user's workstation or inside a desktop app behind NAT or a corporate proxy, **Caretaker initiates all connections**: the orchestrator exposes an HTTPS endpoint (or `http://` on loopback `127.0.0.1` / `localhost` / `[::1]` for local development) and never needs inbound network access to Caretaker.

## Authentication & Transport

- Every request from Caretaker goes to the configured base URL (`{endpoint}`), with trailing slashes stripped before appending `/health`, `/register`, or `/poll`.
- Every request carries `Authorization: Bearer <token>` and `Content-Type: application/json` (for `POST` requests).
- Caretaker applies a 30-second timeout per outbound request and caps accepted in-process response bodies at 1 MB (1,048,576 bytes).

## Endpoints

### 1. Health check

```http
GET {endpoint}/health
Authorization: Bearer <token>
```

Response (`200 OK`):

```json
{
  "ok": true,
  "protocol": 1,
  "name": "Acme Dev Orchestrator"
}
```

- Must require the same bearer token as `/register` and `/poll`, so a `200` proves both reachability and token validity.
- Must have **no side effects** (must not register an instance). Caretaker calls this when the user clicks **Test connection**.
- `protocol` must be `1`; any other value is rejected by Caretaker.

### 2. Register

```http
POST {endpoint}/register
Authorization: Bearer <token>
Content-Type: application/json

{
  "protocol": 1,
  "instanceId": "3ff5e5ff-4423-44fe-b73a-9b3ba88ddbb9",
  "name": "Alice's workstation",
  "version": "0.34.0"
}
```

Response (`200 OK`):

```json
{
  "ok": true,
  "name": "Acme Dev Orchestrator"
}
```

- Idempotent upsert keyed by `instanceId` (a UUID generated once and persisted by Caretaker).
- `name` in the request is a user-editable label and may change on later registrations.
- `name` in the response is displayed in Caretaker's UI next to `Connected`.

### 3. Poll

```http
POST {endpoint}/poll
Authorization: Bearer <token>
Content-Type: application/json

{
  "instanceId": "3ff5e5ff-4423-44fe-b73a-9b3ba88ddbb9",
  "results": [
    {
      "id": "msg-001",
      "status": 200,
      "body": { "ok": true, "task": { "id": "acme-1" } }
    }
  ]
}
```

Response (`200 OK`):

```json
{
  "messages": [
    {
      "id": "msg-002",
      "method": "POST",
      "path": "/api/projects/acme/tasks",
      "body": {
        "title": "Add CSV export",
        "objective": "Export project tasks to CSV",
        "startActive": true
      }
    }
  ]
}
```

- **`results`**: carries every result Caretaker has not yet delivered. Receiving a `2xx` response to `/poll` acknowledges delivery; Caretaker marks those results delivered and will not send them again.
- **`messages`**: array of REST-envelope commands processed sequentially in array order. Each message has:
  - `id` (non-empty string, required) — a message without a usable `id` is dropped and reported as an error.
  - `method` (string, HTTP method).
  - `path` (string, pathname plus optional query string, starting with a single `/`; absolute URLs and `//` prefixes are refused).
  - `body` (JSON value, optional).
- **Cadence**: the configured interval is the *longest* gap between two polls. After a successful poll that leaves Caretaker holding undelivered results (it applied messages, or a person approved or rejected one), Caretaker polls again after a short floor (~250 ms); a failed poll falls back to the interval. An orchestrator can therefore answer a poll that carried a result with the next message of a chain, and the chain proceeds at the speed of the calls. Orchestrators must accept a poll at any time.
- **Unknown instance**: if `/poll` responds with `401`, `403`, `404`, or `409`, Caretaker drops its local registration state and calls `/register` again on the next cycle.

## At-Least-Once Delivery & Deduplication

Delivery from the orchestrator is **at-least-once**:

- The orchestrator **must keep offering a message** on `/poll` until it receives a result for that message `id` in a subsequent `/poll` request's `results` array.
- Caretaker deduplicates by `id` using its persistent ledger:
  - A message waiting for manual user approval (`approve` policy) has no result yet, so the orchestrator keeps offering it and Caretaker safely ignores the duplicate.
  - Once Caretaker has recorded a result (including `400`, `403`, `404`, `413`, or `500`), it will not apply that `id` again while it remains in the ledger.

## Result Statuses

When a message is executed against Caretaker's project/task API, `status` is the HTTP status returned by the route and `body` is the parsed JSON response (or plain text if non-JSON, or `null` if empty).

Statuses generated by Caretaker itself always carry `body: { "error": "<reason>" }`:

| Status | Meaning |
|--------|---------|
| `400` | Malformed message (invalid path, unsupported HTTP method). |
| `403` | The user rejected the message (`approve` policy). |
| `404` | `method` + `path` is not a documented project/task route. |
| `413` | The response body exceeded the 1 MB cap and was dropped. Ask for less: a task thread is read in pages with `GET /api/tasks/{id}/messages?limit=<n>&after=<last id>` (see below). |
| `500` | Caretaker restarted while applying the message; outcome unknown, not retried. |

### Reading long lists

A task thread grows for as long as the task runs, so an orchestrator that mirrors it must page rather than fetch it whole: `GET /api/tasks/{id}/messages?limit=200` for the first page, then `?limit=200&after=<id of the last message received>` until a page comes back shorter than `limit`. To follow the thread afterwards, keep the last id and ask only for what came `after` it. Message ids only grow within a thread, so the cursor never skips or repeats a message. A single page of 200 messages stays far below the 1 MB cap in practice; lower `limit` if a `413` ever comes back. One message can never exceed the cap by itself: caretaker stores at most 100 000 characters of content per message and truncates longer ones with a visible `[truncated: N characters omitted]` marker.

The task list of a project pages the same way, with the task's `seq` as the cursor: `GET /api/projects/{id}/tasks?limit=200&after=<seq of the last task received>`. Without `after` and `limit` both routes answer the whole list, which is fine for a small project and fails with `413` on a large one.

## Allowed Target Routes

Messages may only target Caretaker's documented project/task REST routes (plus `GET /api/openapi.json`, so an orchestrator can discover the full contract through the channel itself).

Everything else — including `/api/fs`, voice, settings, token management, and `/api/orchestrator` — is refused with `404` without touching the server.

## Reference Implementation

Caretaker ships an in-memory reference orchestrator implementing Protocol v1:

```bash
caretaker-cli orchestrator-demo --token my-secret --port 4000
```

The demo accepts an optional `onResult(instanceId, result)` hook (for in-process tests), called when a result is first recorded, before the poll response is built.

See `packages/cli/src/cli/orchestrator_demo.ts` for the complete server implementation, including the admin routes (`GET /instances`, `POST /instances/:id/messages`, `GET /instances/:id/results`).
